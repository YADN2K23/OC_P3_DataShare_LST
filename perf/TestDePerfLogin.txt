1. CONTEXTE ET OBJECTIFS
================================================================================

Ce document présente les détails complets du test de performance du endpoint
de login (POST /api/login) du backend DataShare.

Objectifs:
  - Valider la robustesse du serveur d'authentification
  - Mesurer les temps de réponse du login sous charge
  - Vérifier la stabilité du système avec plusieurs utilisateurs simultanés
  - Identifier les goulots d'étranglement potentiels
  - Garantir les seuils de performance requis (p95 < 300ms, p99 < 600ms)

================================================================================
2. CONFIGURATION DE K6
================================================================================

Outil utilisé: k6 (Load Testing Tool)
Version: Latest (winget install k6)
Framework: JavaScript/ESM

Paramètres de test configurables:
  - BASE_URL: URL du serveur backend (défaut: http://localhost:8080)
  - LOGIN_USER: Identifiant de test (défaut: "demo")
  - LOGIN_PASSWORD: Mot de passe de test (défaut: "demo123")
  - VUS: Virtual Users - Nombre d'utilisateurs simultanés (défaut: 20)
  - DURATION: Durée du test (défaut: 1 minute)

================================================================================
3. DÉTAILS DU SCRIPT DE TEST (login_k6.js)
================================================================================

Fichier: C:\Users\Youssef\DevOps_Dev\Projet 3\DataShare\perf\login_k6.js

Architecture du test:
  - Imports: http (requêtes), check (assertions), sleep (délai entre requêtes)
  - Port de sortie k6 standard

Charge appliquée:
  - Nombre d'utilisateurs virtuels (VUS): 20 par défaut (configurable)
  - Durée: 1 minute par défaut (configurable)
  - Délai entre requêtes: 1 seconde (anti-bot)
  - Timeout: 10 secondes

Payload envoyé:
  {
    "login": "demo",
    "password": "demo123"
  }

Headers HTTP:
  Content-Type: application/json

Seuils de performance (Thresholds):
  - Taux d'erreur HTTP: < 1% (rate < 0.01)
  - Percentile 95 (p95): < 300ms
  - Percentile 99 (p99): < 600ms

Assertions vérifiées:
  1. Status HTTP = 200 (Succès)
  2. Token présent dans la réponse (JWT token valide)

================================================================================
4. MÉTRIQUES SUIVIES
================================================================================

Métriques principales collectées par k6:

1. http_req_duration
   - Définition: Temps total de chaque requête HTTP
   - Percentiles: p50, p75, p90, p95, p99
   - Seuil attendu: p95 < 300ms, p99 < 600ms

2. http_req_failed
   - Définition: Nombre de requêtes échouées
   - Seuil attendu: < 1%

3. Checks
   - "status 200": Pourcentage de réponses avec statut 200
   - "token present": Pourcentage de réponses avec token valide

4. Utilisateurs virtuels (VUS)
   - Nombre d'utilisateurs simultanés actifs

5. Itérations
   - Nombre total de scénarios exécutés

================================================================================
9. TROUBLESHOOTING
================================================================================

Erreur: "Connection refused"
  - Cause: Backend non accessible
  - Solution: Vérifier que le backend s'exécute sur http://localhost:8080

Erreur: "status 200" check failed
  - Cause: Authentification échouée
  - Solution: Vérifier les identifiants (login/password)

Erreur: "token present" check failed
  - Cause: Format de réponse incorrect ou token manquant
  - Solution: Vérifier l'endpoint et le format JSON de réponse

Performance dégradée (p95/p99 élevés):
  - Cause: Charge système élevée, base de données lente
  - Solution:
    * Libérer des ressources système
    * Vérifier les performances de la base de données
    * Réduire le nombre de VUS
    * Optimiser le code backend

Taux d'erreur élevé:
  - Cause: Limite d'utilisateurs simultanés atteinte, problème backend
  - Solution:
    * Réduire le nombre de VUS
    * Vérifier les logs backend
    * Augmenter les ressources serveur
